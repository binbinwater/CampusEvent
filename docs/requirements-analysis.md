# CampusEvent 初始需求分析

## 1. 项目与范围

CampusEvent 是《软件工程》实验二的校园活动报名与管理系统，面向 Student（学生）和 Admin（管理员）两类固定演示角色。学生浏览活动并报名，管理员发布活动并处理审核型报名。

**范围内：**

- 管理员创建、编辑、删除活动，设置名称、类型、时间、地点、人数上限和报名方式。
- 学生按名称筛选，查看活动列表和详情。
- 直接报名自动通过；审核型报名进入待审核。
- 管理员批准或拒绝待审核报名，批准时再次检查名额。
- 学生取消自己的待审核或已通过报名。
- 站内消息通知；通知失败留痕且不回滚报名。
- 查看已通过数、待审核数和剩余名额。

**范围外：** 用户注册、复杂权限、真实邮件/短信、第三方登录、活动签到、支付、移动 App、复杂后台管理。

**角色与固定账号：**

## 2. 功能需求映射

| 编号 | 初始需求 | 实现 |
| --- | --- | --- |
| P2-F01 | 管理员创建、编辑、删除活动 | `/activities/new`、`/activities/<id>/edit`、删除确认页 |
| P2-F02 | 学生浏览活动列表和详情，可按名称筛选 | 活动卡片列表、`?q=` 标题筛选、详情页 |
| P2-F03 | 报名与取消，禁止重复有效报名 | 唯一部分索引 + `RegistrationService` 检查 |
| P2-F04 | 直接报名自动通过；审核型进入待审核 | `DirectRegistrationPolicy`、`ReviewRegistrationPolicy` |
| P2-F05 | 管理员批准或拒绝，批准时再次检查名额 | 审批路由 + `BEGIN IMMEDIATE` 事务 |
| P2-F06 | 四种报名状态及合法转换 | pending / approved / rejected / cancelled |
| P2-F07 | 站内通知 | `MessageNotificationObserver` 写入 `messages` |
| P2-F08 | 按活动查看已通过、待审核和剩余名额 | 活动详情统计卡、管理员总览 |

## 3. 关键业务规则

1. 名额只统计 `approved`；`pending` 不占名额。
2. 报名提交时检查活动是否已开始、是否存在有效报名、当前已通过人数是否小于容量。
3. 直接报名初始状态为 `approved`；审核型初始状态为 `pending`。
4. 审批只接受 `pending`，且必须在同一事务中复核容量；满员时不得批准。
5. 同一学生对同一活动最多一条 `pending`/`approved` 报名；取消或拒绝后保留历史，可再次申请。
6. 学生只能取消自己的 `pending`/`approved` 报名；取消不删除历史记录。
7. 活动开始后不允许新增报名。
8. 已有任何报名记录的活动不得物理删除，避免丢失历史。
9. 报名事务先提交，再发布通知事件；通知失败只记录日志和 `notification_failures`，不回滚报名。
10. 初始版本不提前实现教师 CR；变更版本等待正式 CR 后另建分支。

## 4. 用例说明

### UC-01 浏览和筛选活动

- 参与者：Student、Admin。
- 前置条件：已登录。
- 主流程：进入活动列表 → 输入活动名称关键词 → 系统按标题模糊匹配 → 返回匹配活动的统计和报名状态。
- 备选流程：关键词为空时返回全部活动；无匹配时显示空状态。

### UC-02 学生报名

- 参与者：Student。
- 前置条件：活动存在，未开始，学生没有有效报名。
- 主流程：打开活动详情 → 点击报名 → 服务检查开始时间、重复报名和容量 → 按策略决定初始状态 → 提交报名 → 发布通知事件。
- 备选流程：已开始、重复有效报名、名额已满时拒绝，不写报名记录。
- 后置条件：直接报名为 `approved`；审核型为 `pending`；通过观察者写入站内消息。

### UC-03 管理员审批

- 参与者：Admin。
- 前置条件：报名状态为 `pending`。
- 主流程：管理员在审批中心或活动详情点击批准/拒绝 → 服务开启立即事务 → 读取状态 → 批准时统计已通过人数并复核容量 → 更新状态 → 提交 → 发布通知。
- 备选流程：状态已变化，或批准时已满员，拒绝操作，原状态不变。
- 后置条件：批准为 `approved`，拒绝为 `rejected`，并生成对应消息。

### UC-04 学生取消报名

- 参与者：Student。
- 主流程：学生在自己的报名中点击取消 → 服务校验所有权和状态 → 更新为 `cancelled` → 提交 → 发送取消消息。
- 备选流程：非本人报名、状态已取消/拒绝时拒绝操作。

### UC-05 管理员维护活动

- 主流程：创建/编辑活动，校验字段，容量不得低于当前已通过人数；删除前显示确认页。
- 备选流程：已有报名记录时拒绝删除；表单错误时显示字段级提示。

### UC-06 查看消息与统计

- Student 查看自己的站内消息，并可全部标记已读。
- Admin 查看活动总数、报名总数、已通过数、待审核数，以及每个活动的剩余名额。

## 5. 初始验收用例 C1–C10

| 用例 | 操作 | 预期结果 |
| --- | --- | --- |
| C1 | 管理员创建容量 2 的直接报名活动 | 创建成功并可被学生看到 |
| C2 | 学生 A 直接报名 | 状态“已通过”，站内消息生成 |
| C3 | 学生 A 再次提交相同活动 | 拒绝重复有效报名 |
| C4 | 学生 B 报满后学生 C 再报 | B 通过；C 因名额不足失败 |
| C5 | 学生 A 申请审核型活动 | 状态“待审核”，不占已通过名额 |
| C6 | 管理员批准 A | 状态“已通过”，生成审核消息 |
| C7 | 管理员拒绝另一待审核报名 | 状态“已拒绝”，生成消息 |
| C8 | 批准时容量已满 | 批准失败，不超出上限 |
| C9 | 学生取消待审核或已通过报名 | 状态“已取消”，统计同步变化 |
| C10 | 重启服务后查询 | 活动、报名、通知仍一致 |

## 6. 假设与约束

- 当前交付版本为 `baseline-v1`；附件没有教师发布的 CR，因此没有创建 `change-v2`，也没有伪造变更后材料。
- 日期/时间使用服务器本地时区；系统当前为 Asia/Shanghai。
- 系统是课程演示应用，采用固定演示账号和 HTTP；生产环境需要登录安全、CSRF、权限、HTTPS 和备份设计。
- 数据库为 SQLite；通知和报名使用同一数据库，通知写入在报名提交之后。
