# 需求变更分析（CR 待发布）

## 1. 当前状态

- 当前交付：`baseline-v1`。
- 教师 CR：**未提供**。实验指导书规定 CR 由教师在初版验收后统一发布；附件中没有具体变更内容。
- `change-v2`：未创建，未实现，未伪造。基线标签与变更标签应保持真实可追溯。

## 2. 为什么没有 change-v2

在不知道 CR 的情况下自行实现某个“变更”，会违反“不得获取或针对变更单提前实现功能”的课程规则，也会让新增类数、回归失败数、修改时长等对照指标失去意义。因此当前只完成可验证的初版。

## 3. 变更影响分析模板

收到正式 CR 后，按以下内容填写并另建分支：

| 项目 | 待填写内容 |
| --- | --- |
| CR 编号与描述 | CR-xx：新增/修改的业务规则 |
| 受影响用例 | 报名、审批、取消、通知等 |
| 受影响类/接口 | `RegistrationPolicy`、`RegistrationService`、`Activity` 等 |
| 数据库变更 | 新字段/表、迁移和回填 |
| 策略模式影响 | 是否新增策略实现，是否仍保持容量为公共规则 |
| 观察者影响 | 是否新增事件类型/订阅者，通知失败边界是否保持 |
| 新增测试 | 新规则用例、边界、权限和通知 |
| 回归测试 | 至少重新执行全部 37 条基线测试和 C1–C10 |
| 工作量证据 | Git diff、提交、测试输出、AI 交互记录 |

## 4. 可能的扩展点（未实现）

如果后续 CR 选择以下方向，当前设计提供了明确落点：

1. **报名截止时间**：在 `Activity` 增加字段，在报名服务增加时间窗口公共规则，更新表单、列表和测试。
2. **活动取消**：新增 `ActivityCancelled` 事件，由观察者批量写入取消通知；报名状态转换需要新的服务事务。
3. **候补队列**：新增 `WaitlistedPolicy` 或独立候补服务/状态，需处理顺序、转正和通知；不能简单修改现有策略接口。
4. **通知重试**：将 `notification_failures` 扩展为 outbox，加入重试/幂等键；本次没有提前实现。

这些只是影响分析预案，不是已实现功能。

## 5. 基线可维护性证据

- 策略实现集中在 `campusevent/policies.py`，服务依赖抽象。
- 通知由 `campusevent/events.py` 的发布者/订阅者隔离，报名事务先提交。
- 核心规则测试覆盖 C1–C10，共 37 条自动化测试。
- 任何 CR 实现前先比较基线测试结果，确保回归失败可定位。
